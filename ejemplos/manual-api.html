Manual de integración con la API de facturación

Este manual describe cómo un sistema externo emite, consulta y anula comprobantes a través de la API. Está dirigido a equipos de integración con experiencia previa en servicios HTTP.

Autenticación

Todas las llamadas requieren un token de acceso emitido por el servicio de identidad. El token viaja en la cabecera Authorization con el esquema Bearer y caduca a los sesenta minutos.

No hay refresco silencioso: cuando el token caduca, la integración debe volver a solicitarlo con sus credenciales de cliente. Reintentar la llamada original con un token vencido devuelve 401 indefinidamente.

Emisión de comprobantes

La emisión es asíncrona. El sistema acepta el comprobante, responde 202 con un identificador de seguimiento, y lo procesa por detrás. La respuesta inmediata no significa que el comprobante sea válido: significa que fue recibido.

Consulta del estado

El identificador de seguimiento permite consultar el estado del comprobante. Los estados posibles son recibido, procesando, aceptado y rechazado. Solo los dos últimos son definitivos.

Reintentos del cliente

Si la emisión devuelve un error de red, el cliente puede reintentar con el mismo identificador de idempotencia. El servicio reconoce el reintento y devuelve el resultado original en lugar de emitir un segundo comprobante.

Anulación

Un comprobante aceptado se anula con una nota de crédito, no borrándolo. La anulación es una operación contable con su propio comprobante, y queda sujeta a los mismos plazos que la emisión.

Límites de uso

La API admite sesenta llamadas por minuto y por cliente. Al superarlo responde 429 con una cabecera Retry-After. Esa cabecera es la fuente de verdad: reintentar antes de lo que indica prolonga el bloqueo en lugar de acortarlo.

Ambiente de pruebas

El ambiente de pruebas es funcionalmente idéntico al de producción, pero los comprobantes que emite no tienen validez fiscal. Las credenciales de los dos ambientes no son intercambiables.
